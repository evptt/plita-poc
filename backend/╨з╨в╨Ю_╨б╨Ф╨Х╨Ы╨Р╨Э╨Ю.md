# Бэкенд PoC «Контроль плиты» на Java: что сделано

Основа: разбор ТЗ для бэкенд-команды (К. Идрисов) и отчёт по инфраструктуре PoC (25.10.2026).
Это перенос Python-версии на Java 21 / Spring Boot 3.3. API, форматы и поведение не изменились, поэтому мобильной команде ничего переделывать не нужно.
Результат — папка `backend/`, которая встаёт на место заглушки `infra/backend/`. Править `docker-compose.yml` не нужно.

## 1. Контракт сервиса (отчёт по инфраструктуре)

- [x] Сервис слушает `0.0.0.0:8000`, HTTPS остаётся на Caddy.
- [x] `GET /health` всегда отвечает 200 с `"status": "ok"`. Заодно отдаёт состояние БД и MQTT и счётчики пакетов.
- [x] Логи пишутся в stdout.
- [x] Сервис берёт только переменные, которые уже приходят в контейнер. `DATABASE_URL` в формате `postgresql://user:pass@host/db` сам переводится в JDBC.
- [x] `Dockerfile` двухэтапный: сначала Maven собирает jar, потом он запускается на JRE 21 не от root. Внутри есть HEALTHCHECK.
- [x] Память JVM ограничена под сервер 1 vCPU / 2 ГБ: heap 192 МБ, SerialGC, только C1-компилятор. Ожидаемый расход — около 250–300 МБ.
- [x] Если БД ещё поднимается, сервис ждёт её до 60 с. При обрыве MQTT переподключается сам.

## 2. Схема БД (раздел 5 ТЗ), Flyway

- [x] Таблицы `users`, `homes`, `devices`, `telemetry_history` и индекс `(device_id, timestamp)` создаются миграцией `V1`. Она написана через `IF NOT EXISTS`, поэтому существующую схему из `001_schema.sql` не ломает.
- [x] На уже заполненной базе Flyway ставит baseline 0 и применяет V1 и V2.
- [x] Миграция `V2`:
  - `home_state` — состояние Дома и флаг защиты, переживает перезапуск сервиса;
  - `alarms` — история тревог;
  - `relay_commands` — журнал команд;
  - `devices.home_id` может быть NULL;
  - уникальный индекс на `users.google_id`.
- [x] При старте проверяется, что все колонки из ТЗ на месте. Если нет — понятная ошибка.
- [x] Если в `001_schema.sql` тип устройства объявлен как ENUM, вставка всё равно работает (драйвер с `stringtype=unspecified`).
- [x] ID эмулятора (`emu-sensor-1`, `emu-relay-1`) заводятся при старте.

## 3. MQTT Ingest (раздел 3 ТЗ)

- [x] Сервис подписан на `device/+/telemetry` и `relay/+/power` через Eclipse Paho, с автопереподключением.
- [x] Пакет датчика — 13 байт little-endian: влажность, температура, VOC (float32), радар (uint8, 0–255). Порядок байт настраивается.
- [x] Запись в БД по таблице из разбора ТЗ: val_1 = температура, val_2 = влажность, val_3 = VOC, val_4 = радар. Порядок полей в пакете и в БД разный, это учтено.
- [x] Пакет реле — JSON эмулятора; синонимы полей и текстовый формат `U,I,state` тоже понимаются.
- [x] Что отбрасывается без падения сервиса:
  - битые пакеты (NaN, не 13 байт, кривой JSON);
  - пакеты незаведённых устройств;
  - пакеты, пришедшие не в тот топик.
- [x] Пакеты обрабатываются в отдельном потоке, а не в колбэке Paho. Блокирующая работа в колбэке подвешивает Paho.

## 4. Command Service

- [x] `"0"` и `"1"` публикуются в `relay/{id}/command` с QoS 1.
- [x] По тревоге автоматически уходит `0`. Из приложения можно отправить `0` или `1`.
- [x] Все команды пишутся в журнал с источником (`auto` или `manual`).
- [x] Если реле не выключилось, `0` повторяется, но не чаще раза в 30 с.

## 5. Авторизация и сопряжение (рис. 3)

- [x] `POST /api/v1/auth/google` проверяет Google `id_token`:
  - подпись RS256 по ключам Google (с кешем);
  - срок действия;
  - `aud` равен `GOOGLE_CLIENT_ID` (можно указать несколько через запятую);
  - издателя.

  Затем находит или создаёт пользователя и выдаёт внутренний JWT (HS256).
- [x] Пока `GOOGLE_CLIENT_ID` пуст, вход отвечает 503. Если ключи Google недоступны — тоже 503.
- [x] `POST /api/v1/auth/dev` — вход для разработки. По умолчанию выключен, включается `DEV_AUTH_ENABLED=true`.
- [x] `POST /api/v1/homes` возвращает 201: Дом с датчиком и реле создаётся в одной транзакции.
- [x] Если устройство чужое, уже привязано или другого типа — 409.
- [x] `GET` и `DELETE` для Домов работают; чужие Дома не видны (404).

## 6. Аналитика, OTA, документация

- [x] `GET /api/v1/analytics`: средние значения по интервалам через `date_bin`. Параметры: `home_id`/`device_type` или `device_id`, `from`, `to`, `step`, `points`.
- [x] Заглушки `GET /api/v1/firmware/check` и `GET /api/v1/firmware/download`.
- [x] Swagger UI на `/docs`, схема API — `/openapi.json`.
- [x] Ошибки приходят как `{"detail": "..."}`. Ошибки ввода — 422, нет токена — 401.

## 7. Analysis Engine (раздел 4 ТЗ, рис. 6а/6б)

Алгоритм написан на чистой Java без Spring и полностью покрыт тестами.

- [x] **Этап 1.** K_HT = Hum/Temp, K_VT = VOC/Temp, K_VH = VOC/Hum.
- [x] **Этап 2.** Производные, вес события T = 2 с:
  - отличие от опорной больше 5% — отдельное событие;
  - иначе производные усредняются и T суммируется;
  - коэффициент стабилен при T ≥ 4 с.
- [x] **Этап 3.** Эталоны Варки и Жарки с допуском ±13%; если класс неоднозначен — пересечение HT ∩ VT ∩ VH.
- [x] **Этап 4.** Матрица порогов процесса, правило «И» с мягким допуском. Итог — НОРМА или ТРЕВОГА.
- [x] ТРЕВОГА выносится также:
  - по радару (критическое значение);
  - по опасной динамике: плита включена по просадке напряжения, температура или VOC растут, а движения нет.
- [x] Состояния по рис. 5: Idle → Cooking → Classified → Normal / Alarm → RelayOff → Idle (только ручной сброс). Тревога переживает перезапуск сервиса.
- [x] Сторож связи: если датчик или реле замолчали при включённой плите, приходит уведомление.
- [x] Защиту можно выключить: `PUT /homes/{id}/protection`.
- [x] Все пороги и эталоны лежат в `analysis-params.json`.

## 8. «Красный экран»

- [x] WebSocket `/api/v1/ws?token=<JWT>`. При подключении приходит снимок состояния, дальше — события `alarm`, `state` и обрыв или восстановление связи.
- [x] Если WebSocket не подходит, можно опрашивать `GET /homes/{id}/status`.

## 9. Проверка — что сделано и чего не хватает

Здесь закрыт доступ к Maven Central (`repo.maven.apache.org`), поэтому собрать проект и поднять Spring полностью не удалось. Проверено то, что было возможно:

- [x] **35 юнит-тестов (JUnit 5) пройдены.** Код этих частей и тесты компилировались и выполнялись на JDK 21: алгоритм, разбор пакетов, настройки, загрузка `analysis-params.json`. Пакет реле и файл параметров проверялись на настоящем Jackson. Вместо JUnit работала минимальная замена с теми же `assertEquals`/`assertThrows`.
- [x] **Весь код (75 классов) скомпилирован без ошибок и предупреждений.** Spring, Nimbus, Paho и Hikari при этом подменялись заглушками с их сигнатурами. Это ловит опечатки и ошибки типов в нашем коде, но не проверяет, что сигнатуры заглушек совпадают с настоящими библиотеками.
- [x] **Имена полей JSON проверены на настоящем Jackson со snake_case**: `access_token`, `is_new_user`, `home_id`, `sensor_id`.
- [x] **Логика та же, что в Python-версии**, а та прошла сквозную проверку из 32 пунктов на живых PostgreSQL 16 и MQTT.
- [ ] **Сборка через Maven, запуск Spring и сквозная проверка на Java-версии не выполнялись.** Сделать это у себя:

  ```bash
  mvn test                 # 35 тестов
  docker compose up -d --build
  python tools/e2e_check.py --api https://localhost --mqtt-host localhost ...   # 32 пункта
  ```
  Сквозная проверка (`tools/e2e_check.py`) работает с Java-версией без изменений: API тот же.
- [ ] **Фактический расход памяти не замерен.** Ожидается около 250–300 МБ. Проверить: `docker stats`.

## 11. Что сделать после мержа

1. Сказать админу о переходе на Java: память под Spring, первая сборка займёт 2–4 минуты.
2. Прогнать `mvn test` и `tools/e2e_check.py`.
3. Прописать `GOOGLE_CLIENT_ID`, когда будет OAuth-клиент.
4. Когда заказчик ответит на вопросы из таблицы, обновить `analysis-params.json`.
