# Бэкенд PoC «Контроль плиты»: что сделано

Основа: разбор ТЗ для бэкенд-команды (К. Идрисов) и отчёт по инфраструктуре PoC (25.10.2026).
Результат — папка `backend/`, которая встаёт на место заглушки `infra/backend/` без правок `docker-compose.yml`.

## 1. Контракт сервиса (отчёт по инфраструктуре)

- [x] Слушает `0.0.0.0:8000`, HTTPS остаётся на Caddy.
- [x] `GET /health` всегда отвечает 200 и `"status": "ok"` (по нему проверяет автодеплой). Дополнительно отдаёт состояние БД и MQTT и счётчики пакетов.
- [x] Логи пишутся в stdout.
- [x] Используются только переменные, которые уже приходят в контейнер: `DATABASE_URL`, `MQTT_HOST/PORT/USER/PASSWORD`, `JWT_SECRET`, `GOOGLE_CLIENT_ID`.
- [x] Python/FastAPI занимает ~70 МБ памяти (замерено), так что поднимать тариф сервера не нужно (Java/Spring потребовал бы).
- [x] `Dockerfile`: python:3.12-slim, запуск не от root, встроенный HEALTHCHECK.
- [x] Сервис ждёт, пока поднимется БД (до 60 с), а при обрыве MQTT сам переподключается.

## 2. Схема БД (раздел 5 ТЗ)

- [x] Таблицы `users`, `homes`, `devices`, `telemetry_history` и индекс `(device_id, timestamp)`. Миграции идут через `IF NOT EXISTS`, поэтому на уже созданной схеме из `001_schema.sql` ничего не ломается.
- [x] Миграции применяются при старте сервиса и учитываются в `schema_migrations`. Advisory lock не даёт двум копиям сервиса мигрировать одновременно.
- [x] При старте проверяется, что все колонки из ТЗ на месте. Если нет, сервис падает с понятной ошибкой.
- [x] Новые таблицы:
  - `home_state` — состояние Дома и флаг защиты, переживает перезапуск сервиса (закрывает вопрос 11);
  - `alarms` — история тревог;
  - `relay_commands` — журнал команд реле.
- [x] `devices.home_id` теперь может быть пустым: устройство можно завести заранее и отвязать при удалении Дома.
- [x] Уникальный индекс на `users.google_id`.
- [x] ID эмулятора (`emu-sensor-1`, `emu-relay-1`) заводятся при старте, как просит отчёт.

## 3. MQTT Ingest (раздел 3 ТЗ)

- [x] Подписка на `device/+/telemetry` и `relay/+/power`.
- [x] Пакет датчика: 13 байт, little-endian `<fffB` в порядке «влажность, температура, VOC, радар».
- [x] Запись в БД по таблице из разбора ТЗ: val_1 = температура, val_2 = влажность, val_3 = VOC, val_4 = радар. Порядок полей в пакете и в БД разный, это учтено и проверено тестами.
- [x] Пакет реле: JSON эмулятора `{"voltage","current","state"}`. Записывается как val_1 = U, val_2 = I, val_3 = NULL, val_4 = статус.
- [x] Битые пакеты (не 13 байт, NaN, кривой JSON) и пакеты от незаведённых устройств отбрасываются, сервис продолжает работать.
- [x] Если устройство заведено как датчик, а пишет в топик реле (или наоборот), пакет отбрасывается.

## 4. Command Service

- [x] Публикует `"0"` или `"1"` в `relay/{id}/command` с QoS 1.
- [x] По тревоге автоматически уходит `0`.
- [x] Пользователь может отправить `0` или `1` из приложения.
- [x] Все команды пишутся в журнал с источником (`auto` или `manual`).
- [x] Если реле после тревоги так и не выключилось, команда `0` повторяется не чаще раза в 30 с.

## 5. Авторизация и сопряжение (рис. 3)

- [x] `POST /api/v1/auth/google`: проверяет подпись и срок Google `id_token`, `aud` = `GOOGLE_CLIENT_ID` и издателя. Находит или создаёт пользователя и выдаёт внутренний JWT.
- [x] `GOOGLE_CLIENT_ID` можно задать списком через запятую (Web и Android).
- [x] Пока `GOOGLE_CLIENT_ID` пуст, вход отвечает 503 с понятным текстом.
- [x] `POST /api/v1/auth/dev` — вход без Google для разработки. По умолчанию выключен, включается `DEV_AUTH_ENABLED=true`.
- [x] `POST /api/v1/homes {name, sensor_id, relay_id}` возвращает 201 и создаёт Дом с датчиком и реле в одной транзакции. Если устройство чужое, уже привязано или другого типа — 409.
- [x] `GET /api/v1/homes`, `GET /api/v1/homes/{id}`, `DELETE /api/v1/homes/{id}`. Чужие Дома не видны (404).

## 6. Аналитика и OTA

- [x] `GET /api/v1/analytics`: точки для графиков за период.
  - Устройство задаётся через `home_id` + тип или через `device_id`.
  - Параметры `from`/`to`/`step`/`points`.
  - Агрегация идёт через `date_bin` по индексу `(device_id, timestamp)`.
  - Отдаётся среднее за интервал, для радара и статуса реле — максимум. Работает и для датчика, и для реле.
- [x] Заглушки `GET /api/v1/firmware/check` и `GET /api/v1/firmware/download`.

## 7. Analysis Engine (раздел 4 ТЗ, рис. 6а/6б)

- [x] Этап 1: K_HT = Hum/Temp, K_VT = VOC/Temp, K_VH = VOC/Hum. Деление на ноль защищено.
- [x] Этап 2: производные по паре пакетов, вес события T = 2 с.
  - Если отличие от опорной производной больше 5%, получается отдельное событие.
  - Иначе производные усредняются, T суммируется (4 с) и получается новый опорный пакет.
  - Итог — стабилизированный коэффициент по каждому из трёх графиков.
- [x] Этап 3: сравнение с эталонами Варки и Жарки с допуском ±13%. Если класс неоднозначен, берётся пересечение HT ∩ VT ∩ VH.
- [x] Этап 4: матрица аварийных порогов для найденного процесса, правило «И» с мягким допуском. Итог — НОРМА или ТРЕВОГА.
- [x] ТРЕВОГА по радару: значение из списка «критических».
- [x] ТРЕВОГА по опасной динамике: плита включена, температура или VOC растут, а движения нет дольше заданного окна.
- [x] Плита считается включённой по просадке напряжения от реле. Ток используется как дополнительный признак, его можно отключить.
- [x] Состояния Дома по рис. 5: Idle → Cooking → Classified → Normal / Alarm → RelayOff → Idle. В Idle возвращает только ручной сброс командой `1`. Тревога сохраняется после перезапуска сервиса.
- [x] Сторож связи (вопрос 10): если датчик молчит при включённой плите или молчит реле, в приложение уходит уведомление. Автоотключение плиты в этом случае включается настройкой.
- [x] Защиту можно отключить (вопрос 8): `PUT /homes/{id}/protection`. Анализ и тревоги в приложение продолжаются, но команда 0 автоматически не уходит.
- [x] Все пороги и эталоны вынесены в `app/analysis_params.json`, код при их смене менять не нужно.

## 8. «Красный экран» (вопрос 5)

- [x] WebSocket `/api/v1/ws?token=<JWT>` (Caddy его уже пропускает). При подключении приходит снимок состояния всех Домов, дальше — события `alarm`, `state`, `sensor_offline/online`, `relay_offline/online`.
- [x] Запасной вариант без WebSocket: опрашивать `GET /homes/{id}/status`. Отдельно доступны история тревог и журнал команд.

## 9. Проверка

- [x] 43 юнит-теста: парсеры, JWT и Google, все этапы алгоритма, правила тревоги, состояния, сторож связи.
- [x] Сквозная проверка `tools/e2e_check.py` на живых PostgreSQL 16 и MQTT-брокере, 32 пункта:
  1. вход;
  2. сопряжение и защита от чужих устройств;
  3. пакеты датчика и реле;
  4. аналитика;
  5. радар → команда `0` в реле → тревога в WebSocket → RelayOff;
  6. ручной сброс командой `1`;
  7. битые пакеты;
  8. OTA;
  9. удаление Дома.
- [x] Прогнано на двух вариантах базы: пустой и с заранее созданной схемой (enum для типа устройства, `home_id NOT NULL`, как мог выглядеть `001_schema.sql`). Оба раза всё прошло.
- [x] Прогнано на Python 3.12 в чистом окружении, ровно с `requirements.txt` из образа.
- [x] Отдельно проверено:
  - тревога `RelayOff` сохраняется после перезапуска сервиса;
  - когда брокер выключили и включили снова, бэкенд переподключился сам.
- [ ] Сборка Docker-образа не проверялась: здесь нет Docker. Первый `docker compose up --build` нужно сделать у себя.

## 10. Что приняли сами — нужно подтвердить у заказчика

| № вопроса | Что в ТЗ нет | Что сделано сейчас | Где менять |
|---|---|---|---|
| 2 | Эталоны Варки/Жарки и матрица порогов | Заглушки PLACEHOLDER | `analysis_params.json` → `classification`, `alarm_thresholds` |
| 3 | Формат пакета `relay/power` | JSON эмулятора (и текст `U,I,state`) | `parsers.py` → `parse_relay_packet` |

| 7 | Порог просадки и окно «нет движения» | Номинал 230 В, просадка ≥ 5 В или ток ≥ 0,5 А; окно 300 с; рост ≥ 1 °C/мин или VOC ≥ 10%/мин | `analysis_params.json` → `stove_on`, `dynamics` |

**Внимание:** если эмулятор шлёт в байте радара значение 2, сервер воспримет это как критическую аномалию и выключит «плиту» эмулятора. Это ожидаемое поведение при текущем допущении. Сбросить состояние можно командой `1` из приложения.

## 11. Что сделать после мержа

1. Мобильной команде: эндпоинты, форматы ответов и события WebSocket описаны в `backend/README.md`, полная документация — на `https://<домен>/docs`.
2. Админу:
   - прописать `GOOGLE_CLIENT_ID`, когда будет OAuth-клиент;
   - при желании на время разработки включить `DEV_AUTH_ENABLED=true`, предварительно добавив переменную в `docker-compose.yml`.
3. Когда заказчик ответит на вопросы из таблицы выше, обновить `analysis_params.json`.
